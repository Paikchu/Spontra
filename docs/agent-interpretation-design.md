# 方案：Agent 读表，代码对数

**状态：** 新申报路径已实现（2026-10-23，见文末“实现状态”），旧读取器尚未删除 · **日期：** 2026-10-23 · **起因：** TTMI 连续卡在三处——收入抵销误判、两种分部口径并存、财报稿列头写 “Third Quarter”。每一处都要改代码、升解析器版本、让全部公司重新采集。

## 一句话

每份**新**申报只走一步：**说明每个数字在表里的位置和含义，代码按位置取数，核对能不能对上。** 对上就发布，对不上就保持上一版。已有的报告和已发布的数据不重跑。

## 只处理新申报，不重复跑

- **已发布的数据原样保留。** 切换之前采集到的季度和历史不重新读取，作为新申报核对时的“已发布同期数字”。
- **新申报是指：** 切换之后到达、而且还不是任何已发布季度来源的申报。只有这些走新路径，每份只读一次。
- **不再全量重采。** 现在每次升解析器版本，都会通过 `task.version_changed` 让所有公司重新采集；新路径取消这个机制。读表说明按申报缓存，提示词或核对规则改了，只影响之后到达的申报。
- **只有后台显式操作才会重读旧申报**，即逐份申报的“重新读取”。重读同样走新路径，结果写进这份申报的缓存。

## 三样东西

**输入。** 申报里的表格，附上一季度已发布的科目名和分部名。

**输出：一份读表说明。** 只写位置和含义，不写数值：

- 哪几列是季度，每一列在哪天结束，并引用申报里写这个日期的原文。
- 哪一行是收入、成本、经营利润、税前利润、所得税、净利润，哪几行是分部；分部沿用上季度的哪个名字。
- 哪一行是哪几行的合计，每一行取正还是取负。

**核对：一条规则——对得上。**

- 每个合计都等于它的分项，每一列都要成立。
- 已发布过的同期数字必须相等。只有当收入和净利润与已发布值一致、个别行不同，才视为申报的重述，按最新申报为准；收入或净利润不同就不发布，在后台列出。

## 读表说明从哪来：先免费，后花钱

同一家公司的申报，格式多数季度不变。所以按代价从低到高依次尝试，前一步对上就停：

1. **缓存。** 这份申报已有读表说明，直接用。重采、升版本都不调用模型。
2. **套用上一份。** 把同一公司上一份同类申报的读表说明，按行名、列序套到这份申报上，再用同一条规则核对。对上就用，不调用模型。
3. **只问变了的部分。** 套用后只有个别地方对不上（比如季度结束日不同，或多了一个分部），就只把这几处发给 Agent。财报稿没有申报自带的报告期，期间这一项每次都要问；输入只有列头和含日期的句子，几百个 token。
4. **完整读表。** 新公司、格式大改、或者前三步都没对上时，才把相关表格整体发给 Agent。

旧申报没有读表说明，所以每家公司切换后的第一份新申报无法套用，要走一次完整读表（第 4 步）。不过这时已有已发布数字，下文“只发相关的表”照样适用。从第二份新申报开始，就能套用上一份了。

第 2、3 步不需要按公司或表单写规则：“同一公司、同一类申报的格式通常不变”本身就是通用的事实；即使猜错，核对也会挡住。

## 发给 Agent 的内容尽量少

1. **只发表格，压成紧凑文本。** 去掉 HTML、样式、空列、货币符号，每张表一段制表符分隔的文本。以 TTMI 为例：2026-06-29 的 10-Q 原文 334 万字符，全部 39 张表压缩后只剩 2.5 万字符；10-22 财报稿附件原文 18 万字符，26 张表压缩后 1.2 万字符。
2. **只发相关的表。** 用已发布的数字在全部表格里查找，含有已知数字的表就是候选。这一步与申报类型无关，也不花 token。TTMI 的 10-Q 因此从 39 张表减到 7 张，约 4,500 字符；财报稿减到 2 张，约 5,200 字符。新公司没有已发布数字，就先发目录（只有表名、行名和列头，没有数值），由 Agent 选表，再发它选中的表。
3. **输出只写引用。** 读表说明用表号、行号、列号指向单元格，不复述文字。第 3 步只写和上一份不同的地方。
4. **重试只发差额。** 对不上时只回送不平的等式，不重发表格。系统提示和表格放在每次请求的固定前缀里，重试时命中模型服务的前缀缓存，按缓存价格计费。
5. **低推理档。** 读表是对照，不是推理；默认 deepseek-flash 的低推理档，后台可以按工具改。

## 用量估算

| 情形 | 每份申报的输入 | 预计占比 |
|---|---|---|
| 缓存或套用上一份 | 0 | 大多数 10-Q、10-K |
| 只问变了的部分 | 几百到 2 千 token | 财报稿的期间、个别新行 |
| 完整读表 | 约 3 千到 1 万 token，含提示与相关表格 | 新公司、格式大改 |

作为对照，直接发 TTMI 10-Q 的原始 HTML 约 100 万 token。按 20 家公司、每季约 100 份新申报估算：

- 第一个财报季每家公司各有一次完整读表。
- 之后以套用为主，每季合计在几十万 token 量级。
- 不做历史回填，也不全量重采。

这些数字是估算，实际用量记在 `ai_usage`。

## 不变的

- 归档、完整性门槛、发布、事件、前端，以及 `BusinessFlowQuarter` 合同都不变。
- 分部名沿用上季度，再由“同期数字相等”核对，所以跨年份的分部自然可以比较。

## 删掉的

由读表说明取代：

- 财报稿读取器 `earnings-release.ts`
- 无 XBRL 报表读取器 `statement-table.ts`
- `parser.ts` 里的概念清单、收入拆分取舍规则，以及“全有或全无”
- 第四季度、第一季度推导用的天数窗口（`period-review.ts`、`history.ts`、`derived.ts`）
- ORCL 特例整条路径
- 利润表税后结构判定 `presentation.ts`

## 新增的

- 一个提示词
- 一个核对函数（上面那条规则）
- 一个套用函数（按行名、列序套用上一份读表说明）
- 一张表：按申报保存读表说明、状态和没对上的等式
- 采集里的一步：依次尝试缓存、套用、局部询问、完整读表

模型调用沿用现有封装、每日预算和 `ai_usage` 记账。

## 上线

1. **用一份待读申报验收。** 用 TTMI 10-22 财报稿验收：旧路径读不出它，新路径应发布 2026-09-28 季度，数字与稿内一致；同时记下用了多少 token。不重跑任何已有报告。
2. **切换。** 从这一刻起，新申报走新路径；已发布数据不动；删除上面列出的旧代码和全局解析器版本。
3. **第一个财报季在后台看结果。** 每份新申报的状态是已发布或未对上；未对上的列出不平的等式，季度保持上一版。

## 代价

- 对不上的季度不发布。宁可少一季，也不发布核对不了的数字。
- 新公司的第一份申报没有已发布数字可比，只能靠表内合计对上，而且要走完整读表。
- 已发布的旧数据里如果有旧读取器的错误，不会被自动修正；只有后台逐份重读时才会改正。同期数字核对会以这些旧数据为准，旧数据有错时，新申报会因为对不上而停在上一版，问题在后台暴露出来。

- **读表说明本体**（`workers/analysis/src/financial-data/read-note.ts`）：
  - 紧凑表格，只发送含有已发布数字的表。
  - 读表说明格式与提示词。
