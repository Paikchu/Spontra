# Spontra 产品理念与交互说明

更新日期：2026-10-02。本次将 [Spontra 官网](https://spontra-marketing.max-zhangyuchen.workers.dev/)及用户确认的两个核心卖点同步为项目产品方向，保留此前的持续研究、主动汇报与研究记忆理念。产品目标不等于能力已实现；以下已有实现与交互原型描述沿用此前记录，本次不作运行状态重新验收。技术运行方式见 [README](../README.md)。

## 产品定位

**理解你的交易逻辑，先你一步备好答案，用你喜欢的方式讲清楚。**

英文对外表达：**Understands your logic. Ready before you ask.** 配合说明 **Answers in the format that works for you.**

全天候 AI 伴投 Agent、持续跟进买入理由，是达成这一体验的工作方式。

服务于有自己的投资判断、希望长期检验判断的人。用户提供买入理由、投资期限、仓位约束与风险边界；系统围绕这些前提持续研究，主动提交需要关注和复核的内容。产品承诺应落在证据、跟踪与记忆上，不承诺收益、自动交易或止损保证。

站点的四条主线是自跟随系统、主动汇报、全部持仓、研究记忆与共享研究。“逆向而行，不必独行”意味着在分歧中持续查证；系统需要主动寻找反证，不能只替用户强化既有观点。

## 两个核心产品目标

### 1. 理解交易逻辑，在用户进来前准备好答案

理解的对象是用户为什么投资、在等待什么、什么条件会让判断失效，以及期限、仓位约束和风险边界。系统需要记录尚未确认的前提并接受用户纠正；不能只靠持仓或历史成交推断全部动机。

产品目标是让用户进入 Spontra 时，重要问题与答案已经整理好。系统主动把新证据连接到原始假设，说明“发生了什么、为什么与你有关、支持或挑战哪项判断、接下来复核什么”。未知部分应成为继续研究的问题；没有重要变化时不为数量指标制造消息。

### 2. 按用户偏好沟通，以丰富 UI 帮助理解

同一份研究可以先给一句结论，也可以展开证据对照、趋势图、关系图、时间线或风险条件。视图选择、信息详略与阅读顺序适应用户当前任务，并允许用户自行切换。

个性化改变呈现方式，不改变事实、来源、反证和不确定性。重要证据不能因用户偏好而被隐藏；系统仍应独立挑战原有假设。丰富 UI 的价值是降低理解与核验成本，每个视图都应对应一个明确问题。

## 现有观点是实现核心目标的路径

新增定位保留既有观点，并明确它们如何支撑用户体验：

| 研究路径 | 持续完成的工作 | 对核心体验的贡献 |
| --- | --- | --- |
| 行业追踪 | 跟踪供需、竞争、政策、技术与经营变化 | 提前发现可能影响用户原始假设的新问题 |
| 主动风控 | 核验反证、现金回收、集中度与共同风险敞口 | 在用户设定的边界被触及时准备复核材料 |
| 预期差研究 | 对照原始预期、实际结果与估值可能隐含的预期 | 解释事实变化与预期变化各自的影响，市场预期仍需验证 |
| 决策纪律与情绪校准 | 回看理由、证据和事先设定的复核条件 | 帮助用户区分事实变化与恐惧、兴奋，不替用户做交易决定 |
| 自优化大脑 | 从用户思考、公开研究与真实结果中复盘研究方法 | 提升问题相关性和表达适配，同时保持独立判断 |

自跟随研究与主动汇报负责延续问题；全部持仓帮助识别组合关联；研究记忆保留证据、分歧、版本和后续检查；授权共享研究补充可查证的方法与观点。这些基础继续保留。

自优化大脑的三类输入是：用户确认的投资逻辑与阅读反馈、带出处的公开框架与相反观点、预期与真实结果的对照。修正方法与更新个人偏好应可追溯；修改用户投资原则仍需用户确认。这里描述目标闭环，不宣称已有自动训练、完整个性化或持续自优化能力。

## 核心体验的验收问题

1. 用户没有先提问，打开产品是否已能看到与其判断相关的问题、答案及资料时间？
2. 每项重要变化是否关联到明确的投资假设、期限或风险边界，并保留支持、反证与未知？
3. 切换结论、证据与风险视图后，事实和判断是否一致，来源是否仍可打开核验？
4. 用户纠正假设或补充证据后，后续研究能否接续这一问题，并保留修正记录？
5. 是否明确区分真实产品、体验示意和规划能力？官网的素材预留位不构成实现证明。

以上用于指导后续需求与验收，不能据此将现有原型描述成完整闭环。具体架构见 [自主市场研究系统架构](./autonomous-market-research-architecture.md)。

## 持续在线为什么有用

| 用户面临的问题 | 系统应持续完成的工作 | 用户收到的结果 |
| --- | --- | --- |
| 买入后原来的前提悄悄变化 | 追踪假设、证据、失效条件与待核实事项 | 哪项理由受到支持或挑战，变化从何而来 |
| 项目进度或客户采用尚无最终结果 | 保存未解决问题，在新的披露出现后再次核验 | 接续上次研究的更新，明确已确认与未知部分 |
| 每只股票单看合理，组合却依赖同一前提 | 关联持仓、客户、项目及行业敞口 | 同一事件可能影响哪些持仓及其共同依据 |
| 新闻很多，真正相关的变化很少 | 去重、核验，再匹配个人投资框架 | 与用户有关的变化及值得复核的判断 |
| 换模型或开始新对话就丢失研究上下文 | 保留依据、分歧、版本及预期与结果对照 | 可回溯、可继续的个人研究记录 |

以上是目标行为。定时任务持续运行并不自动意味着这些产品能力已经打通；每项能力都需要独立验收。

## 交互主线：Agent 提交汇报，用户查看与反馈

产品围绕主动提交的内容组织。用户不需要先写提示词才能看到研究进展，也可以在报告下追问、补充依据或纠正原有假设。

1. Agent 发现与用户投资框架有关的变化，形成带证据的汇报。
2. 汇报进入待阅模块，展示具体事件标题、提交者与未读状态。
3. 用户点击模块，在左侧对话区域查看该份每日报告。
4. 其他 Agent 的核验、风险提示或分歧跟随报告展示，保留各自的依据。
5. 用户回复后，后续系统应将需要确认或继续调查的问题纳入跟踪，再以新汇报反馈结果。

其中第 1 步和第 5 步的自动执行尚未实现；当前页面模拟第 2–4 步，并允许本地展示用户回复。

### 四个模块表示四份汇报

右侧四个方块是当日内容入口，每个方块对应一项要汇报的内容。它们不代表四个固定 Agent、四种永久分类或四个独立聊天对象。标题优先表达事件，如“项目延期”“客户采用”，Agent 名称只用于说明谁提交和谁复核。

当前四条预设还包括“共同敞口”“价格疑点”，用于演示不同研究问题，不构成最终 Agent 配置。未来真实汇报的排序、合并、历史归档和超过四条时的展示方式仍需设计。

桌面端左侧展示报告对话、右侧纵向排列四个模块；窄屏允许重排，但必须保留内容选择与对应报告之间的关系。沿用现有 Zinc/Indigo 配色、排版与 Dock，不使用人像、机器人、发光装饰或虚假的工作状态表达智能。

### 一份汇报应回答什么

| 内容 | 要求 |
| --- | --- |
| 事实 | 发生了什么，何时发生，原始材料说了什么 |
| 判断 | 事实支持哪种解释，哪些仍是假设，有无相反证据 |
| 个人影响 | 关联哪项持仓、买入理由、期限或风险约束 |
| 下一步 | 继续核查什么，需要用户确认什么，何种变化值得再次汇报 |
| 依据 | 来源、原文位置、披露时间及核验状态可追溯 |

事实、推断与未知应分别表达。阅读报告不等于用户认可结论；Agent 之间重复同一信息也不能视为独立核验。当前示例中的来源只有占位文字，尚非可追溯的真实引用。

## 能力如何承接产品理念

- **自跟随研究**：财报与监管文件是证据来源之一。电话会、管理层公开信息、项目执行、招聘、客户采用、产品价格等也可作为跟踪线索；是否接入及可靠性需逐项验证。
- **个人框架**：将投资期限、风险偏好、买入理由与仓位约束用于相关性判断。修改投资原则应由用户确认，并保留修正原因。
- **全部持仓**：授权读取后保留账户来源、同步时间与币种，归并相同标的，再检查整体敞口。现有 IBKR 能力是基础，不能据此宣称已接入所有券商。
- **研究记忆**：记录每次判断的证据、分歧、预期、结果和版本。已有财报分析 Memory 是局部能力，完整个人研究记忆仍待设计。
- **共享研究**：仅共享用户授权的方法、观点和资料，保留作者与出处，经过筛选和核验后匹配个人偏好。持仓与私密记录默认不共享是未来功能的设计要求，不代表现有应用已具备个人数据隔离。

现有持仓计划按 ticker 共享且所有访问者可编辑，属于当前运行边界。在实现身份、权限与数据隔离前，不能将它描述为私密个人研究空间。

## 当前代码与建设顺序

当前 `/` 是投资账本，Dock 中的 `/chat` 提供群聊汇报示例。实现见 [`app/chat/page.tsx`](../app/chat/page.tsx) 与 [`app/daily-reports-home.tsx`](../app/daily-reports-home.tsx)。报告、Agent 补充意见与时间均为预设数据；未读和回复仅保存在页面状态中。刷新后恢复初始状态，没有自动生成、持久化、外部推送或回复驱动的 Agent 执行。

以下是建议的建设顺序，不是已经确定的后端架构：

1. **一份真实汇报的完整链路**：选一个明确事件，将原始证据、关联的投资理由与核验结果写成真实报告，接入现有对话页面。验收重点是依据能打开、结论能解释。
2. **持续跟踪与状态保存**：持久化报告、阅读状态、反馈和待核实问题；实现去重与后续更新。验收重点是同一问题能接续研究，已读不等于已解决。
3. **个人框架与组合关联**：接入用户确认的投资前提，说明新事件为何相关，检查多项持仓的共同风险。
4. **研究版本及授权共享**：先实现身份与访问隔离，再完善判断历史、复盘和明确授权的分享。

Agent 的数量、职责拆分、模型、触发方式、通知渠道与报告存储结构尚未确定。群聊中的角色名称是展示原型，不应倒推成必须采用的服务架构。

## 衡量是否做好

优先验证报告是否相关、证据是否可追溯、反证是否被保留、未解决问题是否继续跟踪，以及重复消息是否减少。模型调用次数、Agent 数量和生成报告篇数不能单独证明产品价值。

对外描述需区分“已实现”“示例”“规划”。“全天候”不能替代更新频率和运行状态说明；真实状态未知时，不展示“实时守护”“持续在线”等已完成式承诺。
