# SEC 公司业务报告

SEC 的 Manager → 节点分析 → Review → Synthesis → D1 发布链路继续沿用。研究目标改为解释公司的产品与客户、商业模式、需求与竞争、增长驱动、经营质量，以及投入到现金回报的转化；材料没有披露的维度不补写。

## 模型编排与渲染

Synthesis 可输出 `presentation`，指定 1–12 个章节、章节顺序、flow/grid 排版、compact/comfortable 阅读密度；块类型为 narrative、findings、callout、evidence、metrics、chart。标题与编排由模型选择，正文/要点/证据通过 nodeId 解析，指标通过 metricKey 解析。前端复用 ReportBlockList，SEC 历史图表采用独立的轻量 SVG 渲染，不混用 Yahoo 数据。

所有已完成节点必须被正文、要点或提示覆盖。无效节点/指标、未知块、空章节或遗漏节点使整个编排回退为原报告；旧报告无需数据迁移。模型不能注入 HTML/CSS/JS 或图表数值。可信输出保存在 `PublishedSecReport.presentation`，包含 `sec-presentation.v1` 版本号。

图表可为柱状图或折线图，每图一个指标，最多八期。数值取自通过 XBRL 校验的历史观察，并过滤报告期之后的数据、申报日之后发布的数据和不同单位/币种/口径；至少两期才能画图。同图不混合年度与季度。图表保存其数据快照，附带期间、单位、口径与来源 accession，后续数据更新不会改变旧图。

模型编排之外始终保留全部分析底稿与证据、数据质量、未完成节点、材料清单与 EDGAR 来源。

## 附件和 deck 的覆盖范围

- 10-K、10-Q、20-F 及 8-K、6-K（包括修订）尝试读取同 accession 的完整 SEC submission。
- 正文、可读文本附件（包含 HTML/text 形式的 earnings release、股东信、investor deck）分别记录材料名称、类型与链接，然后合并到同一文本坐标系。节点可以独立选择附件章节。
- PDF/PPT、二进制附件被标记为未解析，不把二进制文本作为财报事实。图片和 XBRL 技术附件不进入正文分析。
- 完整 submission 超过 32 MiB、缺少可读主体或下载失败时回退正文，报告数据质量明确提示附件未覆盖。
- 本次没有检索公司 IR 网站，也没有把另一个 8-K accession 自动并入 10-Q。材料清单只代表实际读到的文件；“已读取文本”不代表所有图片已解析。

接入独立 deck 时，下一步应先建立“公司、财报期、发布日期、来源 URL”的材料关联，使用公司官方 IR/SEC 来源并去重，再加入 PDF 文本和按页 OCR/视觉提取。页面引用需保留页码、来源与提取状态，管理层口径与 SEC 正文冲突需要显式保留。不能仅按最新文件名匹配，否则会把投资者日/不同季度的数据混入本期。

## 生效与验证

这些更改影响下一次生成的定期报告；历史已完成报告仍走旧渲染，不自动批量重算。部署后若需要更新历史报告，应使用现有重算入口对指定 accession 操作。8-K/6-K 保持事件简析流程。

本地验证：TypeScript、定向 ESLint、Vinext 构建；SEC 编排/历史数据/附件/工作流/public API 测试和前端渲染测试。浏览器用合成报告、真实组件与构建 CSS 在 1440px 和 390px 验证图表显示、原始数据展开与无横向溢出。未进行真实模型重算或线上部署，合成页面未覆盖 React 目录控件 hydration。

## 网站视觉一致性

模型只选择章节、密度与组件组合，不接受自定义颜色、字体或 CSS。报告和目录使用网站 primary、foreground、muted-foreground、card、border、radius 等语义主题变量；图表仍为项目内 SVG，来源数据表复用 shadcn Table。浅色/深色和 1440px/390px 的合成报告已做浏览器检查。

## 图文关系

新生成的每个 chart 必须引用一个已完成的 nodeId，并紧跟该节点的 narrative/findings/callout；后端拒绝脱离分析、放在独立图表章节或绑定无效节点的编排，回退完整标准报告。这个检查确保图与文的位置和节点一致，并不等于自动证明业务因果。模型还需判断现有指标是否真的适合业务问题；缺少留存、分部或客户等数据时，不可用总体收入图替代证据。

## 线上生成恢复

若合成报告的 presentation 缺失或校验失败，发布前增加独立的 presentation 工作流步骤。该步骤仅接收已完成节点、允许的块类型、可用指标和历史图表引用；模型只输出编排，正文和数据仍由系统解析。候选与通过校验的编排保存到 R2，失败进入工作流重试，耗尽重试后保留完整标准报告并提示。复核与合成请求最多使用四分钟预算，步骤仍受五分钟截止时间约束。

重试间隔采用一次 30/90/180 秒退避并带抖动，显式关闭平台叠加的指数系数；后备模型遭遇 HTTP 429 时，可在剩余步骤预算内尝试原模型一次。复核与其他分析阶段一样排除 Company Memory，避免旧结论进入本期判断。

## 固定版本与分享

新生成的结构化财报报告使用 `reportVersion = schemaVersion:财报日期-UUID`。
财报日期为 SEC `reportDate`（报告期末日），缺失时使用 `filingDate`；生成时间单独保留在快照摘要的 `generatedAt`。
即使输入、输出和生成时间相同，两次生成仍有不同编码。发布重试复用已生成的编码。

分享地址为 `/analysis/stocks/{ticker}/sec/{accession}?reportDate={date}&reportVersion={version}`。
报告页显示分析编码、生成时间、固定版本入口与复制按钮。后端文件详情 API 支持同名查询参数。
指定版本时只读取持久化快照，并核对 ticker、accession、日期；不存在或不匹配返回 404，绝不退回最新版。
快照包含完整摘要正文、节点证据及结构化报告，存放在现有 `sec_published_reports.payload`，同版本发布不覆盖，不需要数据库迁移。
评估可以直接记录完整 `reportVersion`、分享地址与 `periodId`，分别关联某次文章和同一期财报。

首次上线使用 `node --experimental-strip-types workers/pipeline/scripts/snapshot-current-reports.ts --apply`，仅为每只股票目前最新的已生成报告保存快照；不重跑模型、不补历史期。省略 `--apply` 只预览候选。写入会核对原报告和摘要未变，保留原始记录和生成时间；再次执行跳过已保存的快照。更早的旧记录不提供固定版本分享按钮。
本次不增加评分、反馈或评估执行器。快照固定内容数据；页面渲染样式仍随应用版本变化。

## 按财报期聚合业绩材料

财报阅读与生成单位改为“公司 + 报告期末日”。列表日期使用首次业绩发布日期；不直接比较 SEC 的 `reportDate`，因为 8-K 该字段通常是事件日期，10-Q/10-K 才是财报期末日。

- 10-Q/10-K/20-F 使用申报披露的期末日。8-K/6-K 必须确实发布当期业绩，由单独的分类步骤提供期末日及原文日期证据，并校验原文引用、日期有效性和与申报日期的先后关系；只披露指引、管理层变更或业绩会安排的文件不并入财报。无法确认期末日时保留独立文件，不按相邻日期猜测。
- 同期只有业绩发布时先提供初报；定期报告到齐后，以最新定期报告为生成入口，读取同组各 accession 的正文与可读附件，合成一份报告。来源清单保留各文件日期、原文链接，文本坐标与证据 ID 可追溯；不是把两份已经生成的摘要拼在一起。
- 同期的年度业绩发布和 10-K 共用一个入口。不同公司或期末日不合并；独立事件仍按 accession 单独生成与展示。修订文件保留为来源，最新定期申报作为生成入口。
- 分组元数据存储在现有 `sec_cache` 的 `sec:earnings:{ticker}:{accession}` JSON 记录，分类结果有单独版本键。索引在分组前保存，成员映射使用 D1 batch 写入，不需要新数据库迁移。报告及摘要保存实际使用的来源集合 `inputKey`；来源变化触发重新分析，来源不变且任务完成时跳过。
- API 在数据库分页前去除同组重复文件，总数按财报与独立事件计算。旧 accession 链接解析到同组报告；明确指定日期和版本的历史快照仍读取原快照，不跳到最新报告。新报告未完成时保留已有初报/报告，并显示新增材料待合并。
- 此次不接入电话会、独立 IR PDF，也不改变业务主题遗漏复核机制。当前刷新生成最新定期报告及近期事件；较早报告如需完整重算，使用现有 backfill 流程。已发布快照不会被分组自动改写。

验证覆盖期末日识别与拒绝错误日期、跨申报日合并、年度/季度及公司隔离、独立管理层事件、原文合并坐标、D1 分页/计数、旧链接、初报保留、来源变化重算与工作流去重。前端使用真实组件和模拟 API 在桌面及手机尺寸验证；不代表线上模型重算已经完成。

## 重要披露发现 Agent

研究主线从常规财务指标复述改为“本期有哪些可能改变投资判断的重要细节”。亮点包含利好和风险；不能把“本期存在披露”自动写成“首次披露”或“市场尚未定价”。财务数字继续校验，仅作机制解释的支撑。

生成链路新增：全文分块扫描 → 引用校验与发现清单 → 发现优先的主题规划 → 节点分析 → 独立遗漏审校/补查 → 原有事实复核与合成。8-K/6-K 简析也接收全文发现清单。扫描语义关注客户行为、定价/续约、产品经济寿命、会计估计、合同条款、风险转移、关联事项、交易计划等，开放发现其他主题，不依赖固定关键词命中。

- 每块20,000字符、重叠800字符，两路并发，每块为独立可重试 Workflow 步骤。最多64块，超限或最终失败会发布实际扫描字符数与缺口，不能宣称全文覆盖。覆盖范围仅为已采集的SEC文本，不包含未接入的电话会/IR资料。
- 每个发现必须有40至1600字符的连续原文引用，并通过文字位置及已有证据块校验。伪造引用丢弃并记录警告。保留原文位置、证据ID、问题、重要性及方向；跨块重复发现去重。
- 发现生成专用上下文窗口，绕过原始章节标题丢失问题。high级发现强制纳入计划，通常4至8个主题，上限24；超过预算必须提示，不能用常规数字占满节点预算。
- 独立审校对照发现清单与实际节点正文，可补建此前未规划的主题，最多3个补查。只允许来自已校验发现的ID；不是让模型无依据创建结论。初始节点、补查（round-2）、原有复核修复（round-1）底稿分别保存。
- 分析要求“原文事实 → 为什么重要 → 不能推出什么 → 后续验证”。特别区分会计折旧与经济寿命、交易计划与成交、设立与取消，以及人物职务。压缩片段未找到的信息判为检索缺口，不能标成公司未披露。
- 有已验证原文发现、但缺少XBRL时，允许生成披露型部分报告，不编造财务指标；缺少任何可靠事实仍不发布。扫描或审校不完整会保留警告并标为部分分析，指标已验证不等于重要事项已完整分析。
- 报告及摘要保存 `sec-discovery.v1` 清单，R2保存分块和审校底稿。后台下一次选中旧报告时，缺少该版本的报告会重算一次；历史固定快照保留。未触发较早报告的批量重算。

回归覆盖无标题的设备使用寿命、文件尾部交易计划、伪造引用、跨块去重、扫描失败/预算不足、规划遗漏强制补入、审校补建新主题、缺少财务指标时的披露分析与引用坐标。测试校验编排与引用约束，不代表真实模型的重要事项召回率已通过评估。
